# 断流与保活：一个非浏览器 WebRTC 客户端会踩的坑

> 抓取与观测日期：2026-11-13 ~ 2026-11-14（北京时间）。所有数据来自真实账号 + 真实机位。
> 本文讨论的是「自己实现 ICE + DTLS-SRTP + RTP 的客户端」（不是浏览器、不是官方 App）
> 对接 `gw-*.cg.163.com:6443` 时，为什么会在若干分钟后**静默丢画面**，以及怎么修。
>
> **本文结论已被自己推翻过一轮。** 第一版把「ICE consent / extmap-rtcp-fb / sendrecv」
> 列为三条修复，理由是「这是网页端与自建客户端的可观测差异」。2026-11-14 用改写
> 网页端行为的方式逐条实测，**三条全部不成立**。第 1、3 节保留原推导作为教训，
> 第 7 节是实测记录，第 8 节是现在的结论。

---

## 0. 结论先行（2026-11-14 更新）

**截至本文最后一次实测，根因仍未定位。** 但排查空间已经收得很窄：

| 结论 | 依据 |
|---|---|
| 症状是**网关单方面停推 RTP**，不是会话被回收 | 冻结期间 WS 仍 open、`input` 心跳仍被回显、我们发的 ICE consent **仍被正常回应**（`resp` 与 `sent` 同步递增），只有 RTP 停 |
| 停推**不是**任何一条「网页端有、自建客户端没有」的协议差异 | 11 个假设逐一实测否定，见第 7 节 |
| 官方网页端在同账号同机位能**连续收流 481 s 以上** | 同一套 ticket 接口、同一个 gateway 域名、同一种 `mrfzzmd` 会话 |
| 自建客户端的有效兜底是**主动换会话** | PenCG 的 `ACTIVE_RENEW_MS = 230000`（230 s 主动重连）实测能让用户无感 |

**如果你只是为了「能用」，不要去复刻官方客户端的逐字节行为**——直接按第 9 节的兜底方案做，
把「每 ~250 s 主动换一次会话」当成常规保活手段，成本远低于逐位逆向网关的判活逻辑。

**如果你要继续定位**，第 8.2 节列了剩下的候选方向，按性价比排序。

## 1. 先排除：这几件事**绝对不是**原因

排查「静默停推」最容易走错的四个方向，这里逐条用实测排除。

### 1.1 不是「没响应 DataChannel 握手」

网关会在建连后约 18 s 起，每秒推一次：

```json
{"op":"input","data":{"cmd":"9 25994,1,<4位hex>,<base64>"}}
```

base64 解开恒为 `{"m":"dataChannelReady","pkg":"com.hypergryph.endfield","t":1700000011}`
（同一个 `t` 值**重复推 12 次**后停止；某个会话里推了 32 次）。

**网页端也从不响应它**，并且它照样连着收了 10 分钟。原因在 SDP 里：服务端 offer
**只有 2 个 m 段（audio + video），没有 `m=application` / SCTP**，所以浏览器根本
不会创建 DataChannel（实测 `RTCPeerConnection` 的 `datachannel` 事件从未触发，
`window.__dc` 恒 0）。
`9 …` 这条指令是给「官方原生客户端（走 SCTP）」用的，浏览器端可以直接忽略。

### 1.2 不是「WS 不心跳」

`run.*.js` 里全量搜 `cmd:"0 "` 只有两处：DataChannel 保活、以及 `echoInfo.switch`
的一次性 echo。实测网页端**只在建连时发了 1 次** `{"cmd":"0 1700000010"}`，
网关回显一次，然后 WS 上再也没有任何业务帧，而视频继续流了 8 分钟。

更强的证据：把网页端**所有** `op:"input"` 帧全部丢弃（含那 7 条开播帧和心跳），
仍然连续收流 **481 s**（`video.currentTime` 涨到 477.883，`readyState=4`）。

**结论：WS 通道安静不影响收流。** 不要为了「保活」去加 WS 心跳。

### 1.3 不是「前端无操作超时」（但别和它混淆）

前端自己有一个计时器，参数来自**游戏详情接口**：

```
gameCutTime = { total: 1000*(no_op_duration1 + no_op_duration2),
                warn:  1000*no_op_duration2 }
```

`mrfzzmd` / `wow_cn_high` 实测 `no_op_duration1=480`、`no_op_duration2=120`
→ `total=600 s`、`warn=120 s`。兜底常量在 `.env`：`VUE_APP_CUTTIME_MINUTES=60000`、
`TOTAL=10`、`WRNTIME=2`。

行为：剩 ≤ `warn` 时弹常驻 toast「您还在玩游戏吗？」；到 0 则
`onPostClientError(1002)` + `intervalExitGame()` + ``「由于长时间不操作，已经自动退出」``
+ `closeWindow(10020)`。重置事件：移动端 `touchstart`、PC `keydown`/`click`、
`inputAction` 总线、window `keyup`。

**这是 600 s，而自建客户端实测在 ~250 s 停**，时间尺度差 2.4 倍，不是同一个东西。
（网页端长玩实测确实在 **602 s** 断流，与 `total=600 s` 精确对上——
所以这个计时器是真实存在的，只是它不是自建客户端的那个问题。）

### 1.4 不是「服务端 300 s kickout」（至少在浏览器路径上不成立）

网页端从申请 ticket 起算，在 258 s、300 s、360 s 附近都没有任何异常：
`conn=connected`、`rx` 单调增长、无 `error`、无 `close`。

## 2. SDP 与 getStats 的全量对照（保留作参考）

### 2.1 服务端 offer（约 2,550 B，`a=ice-lite`）

```
a=ice-lite
m=audio 48413 UDP/TLS/RTP/SAVPF 111
a=candidate:1 1 udp 2015364607 27.36.125.184 48413 typ host generation 0
a=ice-ufrag:6N90
a=ice-pwd:jxpQPaD7BUAlPXxXvmJCf4
a=ice-options:trickle trickle
m=video 48413 UDP/TLS/RTP/SAVPF 98 96 107 99 97 108
a=candidate:1 1 udp 2015364607 27.36.125.184 48413 typ host generation 0
```

要点：
- **只有 host candidate**，没有 srflx/relay，端口是网关侧的真实 UDP 端口；
- `a=ice-lite` → 网关不做 connectivity check 的发起方，由客户端提名；
- 音视频复用同一端口（`rtcp-mux`）；
- 视频 6 个 PT（98/96/107/99/97/108），每个都带 `transport-cc` / `goog-remb` / `rrtr`。

### 2.2 浏览器 answer（约 2,705 B）

浏览器回的是 `a=sendrecv` + 原样回显 `a=extmap:*` + `a=rtcp-fb:*` +
`a=ssrc-group:FID` + 两个 `a=ssrc:… cname:` + mDNS candidate。

### 2.3 `getStats()`：20 次 × 5 s 采样（官方网页端）

| 字段 | 起 | 止 | 说明 |
|---|---|---|---|
| `consentRequestsSent` | 5 | 40 | 约 2.5 s 一次，**唯一的周期性双向报文** |
| `responsesReceived` | 6 | 41 | 网关每次都回 |
| `requestsReceived` | 1 | 1 | 网关只发过一次 Binding Request |
| `responsesSent` | 1 | 1 | 我们只回过一次 |
| `bytesSent` | 9,481 | 41,277 | 全是 STUN + DTLS，**几乎不发 RTP** |
| `bytesReceived` | 60,549 | 2,3xx,xxx | 视频下行 |
| `inbound-rtp.video.pliCount` | 0 | **0** | 浏览器一次 PLI 都不发 |
| `inbound-rtp.video.nackCount` | 0 | **0** | 一次 NACK 都不发 |
| `remote-inbound-rtp` | — | **始终缺失** | 网关从不发 RR |

**这张表是后面所有二分实验的出发点**：如果「不发 PLI/NACK/RR」是问题，
那官方网页端自己就该出问题。

## 3. 一个常见的错误推导（保留作教训）

第一版结论是这么来的：

> 网页端 consent 在涨、answer 是 sendrecv + 带 extmap/rtcp-fb，
> 自建客户端三样都没有 → 那一定是这三样的锅。

这个推导错在**把「可观测差异」等同于「致因」**。三处差异确实存在，
但它们只是「网页端恰好这么做」，不是网关判活的依据。要证伪它们，
唯一有效的办法是**让网页端也这么做**，然后看它是否照样断——第 7 节的
`MUNGE=flags` / `MUNGE=full` 就是这个实验。

**教训：想验证「X 是原因」，去掉 X 看是否复现，比「加上 X 看是否消失」更可靠。**
因为「加上 X 之后不断了」可能只是 X 顺手带出了别的效果（比如重连换了新机位）。

## 4. 三条「会话结束」路径，别漏监听

排查停推时如果只监听 `op:"error"`，会漏掉「礼貌下线」这条，
把正常结束误判成网络故障，从而触发不必要的重连逻辑。

| 路径 | 报文 | 前端行为 |
|---|---|---|
| 服务端回收机位 | `op:"error"`，`errcode` ∈ {**403**, **1213**} | 弹「由于您太久没回来游戏已关闭…」，并**自己重 POST tickets 拿新机位** |
| **服务端正常结束** | **`op:"close"`，`{code:0, reason:"normal"}`** | `onGameStop` + `onClose`，**不弹窗、不重连** |
| WS 断开 | `onclose`（无报文） | 显示「正在尝试重新连接，请稍候」，重连 3 次后报 1004 |

`op:"close"` 的真实抓包（2026-11-13，同一次会话）：

| 相对时刻 | 事件 |
|---|---|
| 406.9 s / 412.1 s | `games_playing_status` 里仍是当前会话 |
| 413.199 s | `games_playing_status` 变 `games_playing: []`（机位被摘除） |
| 413.203 s | `op:"message"`（活动领奖通知，与断流无关） |
| 413.255 s | `op:"close"` `{code:0, reason:"normal"}` |
| 413.263 s | 浏览器 `ws-close`，`video.currentTime` 仍靠本地缓冲继续涨 |
| 418.651 s | 同一 token 下出现**另一个 `play_id`** 的会话（被人/别的进程接管） |

**这条路径的特征是：音视频同时停、WS 立刻 close、并且 `games_playing` 已被清空。**

`errcode` 速查：

| errcode | 含义 | 正确反应 |
|---|---|---|
| **403** | 机位没了 / 被回收 | 重新 `POST tickets`，不要原地重连 |
| **1213** | ticket 失效（ttl 24 s）或机位已被抢 | 重新申请机位 |
| **1811** | 上一局还没退干净 | `DELETE api/v2/users/@me/games-playing/<code>` 等 4~6 s 再申请 |
| **1288** | 没有可用 region | 先测速再申请（`regions` 不能为空数组） |
| **0 + `reason:"normal"`** | 正常结束会话 | 走 `onGameStop`，不当故障处理 |

## 5. 保活清单（按「实测有效」排序）

对接 `gw-*.cg.163.com:6443` 时：

1. **主动换会话是最可靠的保活。** 每 ~230 s 重新 `POST tickets` + 重连，
   用户侧几乎无感（PenCG 实测）。这条不需要理解网关的判活逻辑。
2. **WS 不需要定期心跳。** 头 20 秒之后完全静默是正常现象，网页端就这样。
3. **DataChannel 可以不实现。** 浏览器路径根本没有 SCTP m 段；`9 …` 指令直接忽略。
4. **`op:"close"` 要当成终止信号**，和 `op:"error"` 分开处理。
5. **`op:"error"` 的 403 / 1213 是「机位没了」**，正确反应是重新申请机位，不是重连。
6. **`regions` 必须给具体 region code**，空数组会 `404 errcode=1288`。
7. **ticket ttl 只有 24 s**，申请后要立刻 auth，否则 `1213 ticket required`。
8. **RTCP RR / NACK / PLI 是协议义务**（弱网补帧确实需要），但**不是保活手段**：
   网页端一次都不发也能收流 8 分钟；自建客户端全关掉也照样在 250 s 停。
9. **ICE consent 要发**（RFC 8445 §11 的正当行为，且实测网关会正常回应），
   但**发不发不影响停推**。

## 6. 复现方法

```python
import sys; sys.path.insert(0, 'sdk')
from cgapi import make_api

a = make_api()                      # 自动从本机 Chrome 读 token
detail = a.get('api/v1/games/mrfzzmd')
regions = [s['region'] for s in a.media_servers('mrfzzmd')][:1]
tk = a.post_ticket('mrfzzmd', regions=regions, codecs=['h264'],
                   width=1280, height=720)
print(tk['gateway_url'], tk['lock_detail'])   # ticket ttl 仅 24 s
```

拿到 `gateway_url` 后：
1. WS 连上去，**首包 auth 必须明文**（`{"op":"auth","data":{user_id,token,game_code,…}}`）；
2. 之后全部走 `offsetEn(OFFSET, json)`，`OFFSET = get_offset2(cookieGet('NCG-eid')) % 256`；
3. 收到 `op:"offer"` 的 SDP → 建 ICE（ice-lite，主机提名）→ DTLS → SRTP-SAVPF；
4. 观察 `inbound-rtp.bytesReceived` 是否在某个时刻停止增长。

## 7. 2026-11-14 逐项实测：11 个假设，全部被排除

**方法**：所有实验都在**官方网页端**上做（Playwright + iPhone 14 UA + 真实账号 + 真实机位），
用 `addInitScript` 改写网页端发出的报文/SDP，把它改成「自建客户端的样子」，
看官方网页端是否也复现「约 250 s 静默停推」。如果复现 → 假设成立；如果照常连播 → 排除。

这种做法的好处是不需要改一行 native 代码，也不受词典笔硬件影响；
代价是每轮都要重新申请机位（ttl 24 s），而且**必须确认没有第二个客户端在用同一账号抢机位**
（否则每轮都会被顶掉，得到一堆假结论——踩过三次）。

| # | 假设 | 实验 | 结果 | 结论 |
|---|---|---|---|---|
| 1 | 没建 DataChannel | 网页端本来就不建（offer 无 SCTP 段） | 连播 10 min | ❌ 排除 |
| 2 | WS 不心跳 | 网页端本来只发 1 次 | 连播 10 min | ❌ 排除 |
| 3 | 前端 600 s 无操作超时 | 时间尺度对比 | 网页端 602 s 断（对上了），自建客户端 250 s | ❌ 排除 |
| 4 | 服务端 300 s kickout | 258/300/360 s 观察 | 无异常 | ❌ 排除 |
| 5 | 缺 ICE consent | 给 native 补 2.5 s 周期 consent | `resp` 从 #1 涨到 #109，网关全回；**仍在 4m19s 冻结** | ❌ 排除 |
| 6 | answer 不回 `a=extmap`/`a=rtcp-fb` | `MUNGE=flags`：从 answer 里删掉 5 条 extmap + 19 条 rtcp-fb | 连播 **481 s**，`ct=477.883` | ❌ 排除 |
| 7 | answer 是 `a=recvonly` | `MUNGE=full`：再把 `sendrecv` 全改 `recvonly` | 跑到 **354 s** 仍正常（`ct=308.858`） | ❌ 排除 |
| 8 | 上行 RTCP（RR/NACK/PLI）扰乱了网关 | 给 native 加 `noRtcp` 开关，PLI/RR/NACK 全关（consent 保留） | `PLI sent`=0、`RR sent`=0，**仍在 247 s 冻结** | ❌ 排除 |
| 9 | 游玩期不轮询 HTTP，被判挂机 | 记录网页端所有 `/api/` 请求 | 31 个请求全在开头 16 s，之后**零请求**；`users/@me/status` 从未出现 | ❌ 排除 |
| 10 | auth 之后不发任何 input 帧 | 丢弃全部 `op:"input"`（7 条开播帧 + 心跳） | 连播 **481 s**，`ws-close` 为 0 | ❌ 排除 |
| 11 | auth 包内容不同（缺 `fps`/`apk_decoder`，platform 4→1，codecs 15→1，quality high→low，w 1476→1280） | `MUNGE=all`：把网页端 auth 改写成完全等于 native 的形态 | 连播 **284 s**，`ct=284.84`、`rx=50,992,259`，258 s 节点 `ct=254.787` 完全正常 | ❌ 排除 |

第 11 条是最后一条「协议层可见差异」。改写后的 auth 实测报文（token 打码）：

```json
{"id":"<Date.now()>","op":"auth","data":{
  "user_id":"…","token":"<token>","game_code":"mrfzzmd",
  "w":1280,"h":720,"quality":"low","codecs":["h264"],"platform":1}}
```

——与自建客户端发出的完全一致，网关接受（回了 `op:offer`），并且不因此停推。

### 7.1 一个重要的附带发现

冻结期间我们发出的 ICE consent **仍然被网关正常回应**：

```
[cgmedia] #1 ICE consent sent (#97, every 2500ms) resp=98  rxStun=108
（此时 RTP 已停了 12 s）
```

说明**网关没有把这个会话丢弃**，UDP 五元组是活的、我们的报文它照收照回。
它是**单独停掉了 RTP 的推送**。

这条事实很重要：它排除了「会话被回收 / NAT 超时 / 端口失效」这一大类解释，
把问题锁定在网关**媒体层**的某个判定上。

## 8. 现在的判断

### 8.1 已确定的事实

1. 官方网页端（Chrome）在同账号、同 ticket 接口、同 gateway 域名、同 `mrfzzmd` 会话下，
   **能连续收流 481 s 以上**，且在 8 分钟窗口内不出现任何停推；
2. 自建客户端每次都停在 **~250 s**（实测 247 / 248 / 253 / 258 / 259 s），
   `rx` 冻结、`fps` 归零，但 WS 健康、consent 被正常回应；
3. 第 7 节 11 个假设全部排除，其中包含所有「网页端发/收、自建客户端不发/不收」的报文级差异。

### 8.2 剩下的候选方向（按性价比排序）

1. **DTLS 层的差别。** 自建客户端的 DTLS 是手写的（`cm_dtls.c`），Chrome 是 BoringSSL。
   可能的差异点：DTLS 1.2 与 1.3 的选择、cipher suite 顺序、`use_srtp` 扩展里
   protection profile 的顺序（`SRTP_AES128_CM_HMAC_SHA1_80` vs `_32`）、
   证书自签名字段、`extended_master_secret`。**网关有可能按 DTLS 指纹做风控**。
   验证方式：抓两边 ClientHello 逐字段 diff。
2. **SRTP 的 ROC / 重放窗口。** 自建客户端 `idx = ((roc<<16)|seq)` 用的是自己维护的 ROC，
   如果 24 bit 序列号回绕（65536 包）时 ROC 没加，之后所有包的索引都会错。
   按实测码率估算，250 s 量级正好接近第一次回绕的位置（视频 ~125 pkt/s + 音频 ~50 pkt/s）。
   **这个假设的时间尺度与症状吻合得最好，建议优先验证。**
   验证方式：在 `cm_srtp_unprotect` 里打印 `seq`、`roc`，看冻结前后是否正好跨过 `seq=0`。
3. **UDP 发送缓冲区 / 接收窗口。** 自建客户端只读不写，如果 socket 的 rcvbuf 被写满
   而内核丢弃，会出现「网关还在发但我们不涨」——但本项目的 `rxStun` 同步增长说明
   socket 仍在被正常读取，这个假设较弱。
4. **网关按 `pkg` / `game_code` 的分档策略。** `op:result` 里会回
   `{"container":"topa10_…" , "encoder":"high,None", "host":"ahnfs10000"}`，
   `encoder` 是网关侧编码器的实际选择。若某个会话被分到特定的 encoder 组合，
   可能是那一档的策略问题。验证方式：记录每轮的 `encoder` 值与冻结时刻的相关性。

### 8.3 工程上的建议

在根因定位之前，**用主动换会话兜底**：每 ~230 s 主动 `POST tickets` + 重连网关。
用户侧的表现是「画面卡 1~2 秒」，比「4 分钟后彻底冻结」好得多。

| `longplay.js` / `longplay2.js` | 网页端长玩对照，每 5 s 采样 `currentTime` / `bytesReceived` |
| `sdp_probe.js` | 导出 `server-offer.sdp` / `client-answer.sdp` + 20×5 s `getStats` + WS 帧 |
| `pencg_shape.js` | 把 Chrome 的 answer 改写成自建客户端形态（`MUNGE=flags|full|off`） |
| `no_input_probe2.js` | 丢弃 `op:"input"` 帧（`DROP=all|sel|burst|off`） |
| `poll_probe.js` | 记录游玩期所有 `/api/` 请求 |
| `pencg_auth_probe.js` | 把 auth 改写成自建客户端形态（`MUNGE=all|nofps|nodecoder|plat|codecs|quality|wh|off`） |

前三个是观测，后四个是二分实验。全部用 `require('../env/node_modules/playwright-core')`，
`executablePath` 指向本机 Chrome。

**跑实验前必须确认没有第二个客户端在用同一账号**，否则每轮都会被 `games_playing_status`
顶掉，得到的全是假结论（本轮踩过三次，三次结论全部作废）。
