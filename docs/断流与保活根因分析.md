# 断流与保活：一个非浏览器 WebRTC 客户端会踩的坑

> 抓取与观测日期：2026-11-13（北京时间）。所有数据来自真实账号 + 真实机位。
> 本文讨论的是「自己实现 ICE + DTLS-SRTP + RTP 的客户端」（不是浏览器、不是官方 App）
> 对接 `gw-*.cg.163.com:6443` 时，为什么会在若干分钟后**静默丢画面**，以及怎么修。

---

## 0. 结论先行

网页端在不建 DataChannel、不发任何 WS 心跳的情况下能连续收流 10 分钟以上；
`getStats()` 里唯一一直在走的「保活」是 **ICE consent（STUN Binding，约 2.5 s 一次）**，
并且 SDP 协商是 **`sendrecv` + `transport-cc` 双向**。

所以，一个「只发一次 STUN 就转 DTLS、之后全靠 UDP 收流、answer 里回 `recvonly`、
不回 `a=extmap` / `a=rtcp-fb`」的客户端，与网页端存在三处**可观测**差异。
按性价比排序的修复：

| 优先级 | 改什么 | 为什么 | 验证方式 |
|---|---|---|---|
| **1** | 会话期每 ~2.5 s 发一次带 MESSAGE-INTEGRITY 的 **STUN Binding Request** | 网页端 `consentRequestsSent` 单调递增，是唯一的周期性双向报文 | 改完若「约四分钟停推」消失，即定案 |
| **2** | answer 里**原样回显** offer 的 `a=extmap:*` 与 `a=rtcp-fb:*`（尤其 `transport-cc`），并真的发 TWCC 反馈 | 网关 offer 里每个视频 PT 都带全套 `transport-cc` / `goog-remb` / `rrtr`，客户端全静默等于「不报告接收质量」 | 抓包确认 answer 里有 extmap/rtcp-fb；`getStats` 侧看 REMB/TWCC 是否被网关调整码率 |
| **3** | `a=recvonly` → **`a=sendrecv`** | 网页端就是 `sendrecv`；`recvonly` 可能让网关不把你当成「活跃订阅者」 | answer 改完观察是否仍停推 |

三者可以独立验证，**先只做第 1 条**（改动最小：一个定时器 + 复用已有的 STUN 构造函数）。

---

## 1. 先排除：这几件事**不是**原因

排查「停推」时最容易走错的四个方向，这里逐条用实测排除。

### 1.1 不是「没响应 DataChannel 握手」

网关会在建连后约 18 s 起，每秒推一次：

```json
{"op":"input","data":{"cmd":"9 25994,1,<4位hex>,<base64>"}}
```

base64 解开恒为 `{"m":"dataChannelReady","pkg":"com.hypergryph.endfield","t":1700000011}`
（同一个 `t` 值**重复推 12 次**后停止）。

**网页端也从不响应它**，并且它照样连着收了 10 分钟。原因在 SDP 里：服务端 offer
**只有 2 个 m 段（audio + video），没有 `m=application` / SCTP**，所以浏览器根本
不会创建 DataChannel（实测 `RTCPeerConnection` 的 `datachannel` 事件从未触发）。
`9 …` 这条指令是给「官方原生客户端（走 SCTP）」用的，浏览器端可以直接忽略。

### 1.2 不是「WS 不心跳」

`run.*.js` 里全量搜 `cmd:"0 "` 只有两处：DataChannel 保活、以及 `echoInfo.switch`
的一次性 echo。实测网页端**只在建连时发了 1 次** `{"cmd":"0 1700000010"}`，
网关回显一次，然后 **29 秒之后 WS 上再也没有任何帧**（`sent` 11 帧 / `recv` 28 帧
全部集中在头 29 秒），而视频继续流了 10 分钟。

**结论：WS 通道安静不影响收流。** 不要为了「保活」去加 WS 心跳。

### 1.3 不是「前端无操作超时」（但别和它混淆）

前端自己有一个计时器：

```js
interval:function(){ /* 每 gameCutTime.warn 走一格 */
  if((this.intervalTime -= this.gameCutTime.warn) <= 0){
    this.closeInterval(); this.onPostClientError(1002); this.intervalExitGame();
    this.$confirm({message:"由于长时间不操作，已经自动退出", …}); } }
```

`gameCutTime` 来自游戏详情的 `no_op_duration1 + no_op_duration2`（实测 `480 + 120`），
即 **total = 600 s、warn = 120 s**。重置它的事件是 `touchstart`（移动端）/
`keydown`+`click`（PC）。

13 分钟实测里这条路径精确落在 **602 s**：两次 `pageerror` + 网关 WS `close`，
605 s 起页面出现「长时间不操作」。**它是客户端自杀，不是服务端断流**，而且
`video.currentTime` 之后还在涨（本地缓冲）。

### 1.4 不是「服务端 300 s kickout」（至少在浏览器路径上不成立）

网页端同样从 `/api/v2/tickets` 起算，258 s 时毫无异常。若服务端真有 300 s
闲置踢人，浏览器端也应该在 4 分多钟被杀——但实测到 600 s 都是 1.5–2.9 MB/5s
的稳定码率。

## 2. 真正的差异：SDP 与 getStats 的全量对照

### 2.1 服务端 offer（2,550 B，`a=ice-lite`）

```
a=group:BUNDLE 0 1
a=ice-lite
a=ice-options:trickle trickle
a=msid-semantic: WMS ARDAMSa0 ARDAMSv0
m=audio 36757 UDP/TLS/RTP/SAVPF 111
a=rtpmap:111 opus/48000/2
a=fmtp:111 maxaveragebitrate=128000;sprop-stereo=1;useinbandfec=1
a=rtcp-fb:111 transport-cc
a=extmap:2 urn:ietf:params:rtp-hdrext:ssrc-audio-level
a=extmap:9 http://www.ietf.org/id/draft-holmer-rmcat-transport-wide-cc-extensions-01
m=video 36757 UDP/TLS/RTP/SAVPF 98 96 107 99 97 108
a=rtpmap:98 H264/90000      a=fmtp:98 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42e01f
a=rtpmap:96 VP8/90000
a=rtpmap:107 H265/90000     a=fmtp:107 level-id=93;tx-mode=SRST
a=rtpmap:99 rtx/90000  a=rtpmap:97 rtx/90000  a=rtpmap:108 rtx/90000
a=rtcp-fb:98 ccm fir / nack / nack pli / goog-remb / rrtr / transport-cc   （96、107 同样全套）
a=extmap:11 http://www.ietf.org/id/draft-holmer-rmcat-transport-wide-cc-extensions-01
a=extmap:12 http://www.webrtc.org/experiments/rtp-hdrext/playout-delay
a=extmap:13 urn:ietf:params:rtp-hdrext:generic-frame-descriptor-00
a=setup:actpass
candidate:1 1 udp 2015364607 112.90.x.x 36757 typ host
```

要点：

- **只有 2 个 m 段，没有 SCTP。**
- 每个视频 PT 都有 **完整的 `ccm fir` / `nack` / `nack pli` / `goog-remb` / `rrtr` / `transport-cc`**。
- 有 `transport-cc` 的 extmap（audio 9 / video 11），说明网关期待客户端**周期性回 TWCC**。

### 2.2 浏览器 answer（2,705 B）

- `a=setup:active`、**每段 `a=sendrecv`**；
- **逐段回显全部 `a=extmap`**（audio 2/9，video 11/12/13）；
- **逐 PT 回显全部 `a=rtcp-fb`**（`goog-remb` / `transport-cc` / `ccm fir` / `nack` / `nack pli` / `rrtr`）；
- H264 fmtp 追加 `x-google-start-bitrate=1000;x-google-max-bitrate=2800;x-google-min-bitrate=1000`；
- H265 fmtp 改写 `level-id=93;profile-id=1;tier-flag=0;tx-mode=SRST`。

### 2.3 `getStats()`：20 次 × 5 s 采样

| 指标 | 观测 |
|---|---|
| `candidate-pair.consentRequestsSent` | **5 → 40，单调递增（≈每 2.5 s 一次）** |
| `candidate-pair.responsesReceived` | 6 → 41（网关每次都回） |
| `candidate-pair.requestsReceived` / `responsesSent` | 恒 1 / 1（网关几乎不主动发 STUN） |
| `inbound-rtp.pliCount` / `nackCount` | **全程 0** |
| `remote-inbound-rtp` | 全程缺失（网关从不发 RTCP RR） |
| `outbound-rtp(kind=video).bytesSent` | 恒 0（纯下行） |

**两个反直觉但关键的结论**：

1. **网关不靠 RTCP 反馈判活。** 浏览器一次 PLI/NACK 都没发，照样收 10 分钟。
   所以「补 RTCP RR / NACK」不会解决停推（可以补协议义务，但别指望它治这个 bug）。
2. **唯一的周期性双向报文是 ICE consent。** 浏览器每 2.5 s 发一个 STUN Binding
   Request，网关每次都回。这是全网关层面唯一「你不发就没人知道你还在」的东西。

## 3. 自建客户端的典型缺口

一个「只做够连通性检查」的实现通常长这样：

```c
/* 1) 向网关 host candidate 发一次带认证的 Binding Request */
/* 2) 收到 0x0101 Binding Success Response → 认为连通 */
/* 3) 转 DTLS-SRTP，之后只收流 */
```

然后 answer 里写：

```
m=audio 9 UDP/TLS/RTP/SAVPF 111
a=recvonly
a=rtcp-mux
...
m=video 9 UDP/TLS/RTP/SAVPF 98
a=recvonly
...
```

缺失点一目了然：**没有会话期 STUN、没有 extmap/rtcp-fb 回显、不是 sendrecv。**

有意思的是，「发 STUN」的能力往往**已经写好了**——只是没人在会话期调它。
比如典型实现里已经有：

- `cm_stun_handle()`：收到网关的 Binding Request 会正确回 `0x0101` + XOR-MAPPED-ADDRESS
  + MESSAGE-INTEGRITY + FINGERPRINT（所以网关发来的 STUN 能被回应）；
- `ice_send_binding(sess, key, with_change_req, as_controlled)`：完整构造 USERNAME /
  PRIORITY / ICE-CONTROLLING / USE-CANDIDATE / MESSAGE-INTEGRITY / FINGERPRINT。

**补丁只需要一个定时器**（伪代码）：

```c
/* 在 cm_ice_run() 成功之后启动；在会话结束时取消 */
static void ice_consent_timer_cb(void *arg) {
    cm_sess *s = arg;
    /* with_change_req=0, as_controlled=0：与初次连通时完全相同的报文形态 */
    ice_send_binding(s, s->ice_key /* ice-pwd */, 0, 0);
    cm_timer_after(s, 2500, ice_consent_timer_cb, s);
}
```

注意三点：

- **key 用 `ice-pwd`**（answer 里公布的那个），不是网关的密码；
- **`as_controlled` 保持 0**（我们用 ICE-CONTROLLING + USE-CANDIDATE 提名的角色），
  除非网关回过 487 Role Conflict；
- 响应（`0x0101`）在媒体期可以直接丢弃，**但日志里要能看见它在回**——
  这是验证 patch 生效的最快信号（`rx_kept++` 之类）。

### 3.1 第 2 条修复的具体形态

`buildAnswer()` 里按 offer 的 m 段逐段处理时，除了 rtpmap/fmtp，还要：

```js
// 逐段：把 offer 里属于该 m 段的 extmap / rtcp-fb 原样搬过来
for (const line of offerLinesOf(seg)) {
  if (line.startsWith('a=extmap:'))  out.push(line);
  if (line.startsWith('a=rtcp-fb:')) out.push(line);
}
// m 段方向
out.push('a=sendrecv');   // 不是 recvonly
```

native 侧要**真的用起来**：

- 按 `extmap` 的 id 解析 RTP 头扩展里 transport-cc 的 seq（每包一份）；
- 每 100 ms 打包一条 TWCC 反馈（RTCP PT=205，FMT=15，`transport-cc`），
  内容至少包含收到的包 seq 与到达时间；只在收到包时才发，没包就别发假反馈。

如果 native 侧短时间做不完 TWCC，**至少先把 extmap/rtcp-fb 回显上**——让网关看到
「这个对端声明了 transport-cc」，比完全静默好。

## 4. 还有两条「会话结束」路径，别漏监听

排查停推时如果只监听 `op:"error"`，会漏掉下面这条「礼貌下线」，把正常结束误判成
网络故障，从而触发不必要的重连逻辑。

| 路径 | 报文 | 前端行为 |
|---|---|---|
| 服务端回收机位 | `op:"error"`，`errcode` ∈ {**403**, **1213**} | 弹「由于您太久没回来游戏已关闭…」，并**自己重 POST tickets 拿新机位** |
| **服务端正常结束** | **`op:"close"`，`{code:0, reason:"normal"}`** | `onGameStop` + `onClose`，**不弹窗、不重连** |
| WS 断开 | `onclose`（无报文） | 显示「正在尝试重新连接，请稍候」，重连 3 次后报 1004 |

`op:"close"` 的真实抓包（2026-11-13，同一次会话）：

| 相对时刻 | 事件 |
|---|---|
| 406.9 s / 412.1 s | `games_playing_status` 里仍是当前会话 |
| 413.199 s | `games_playing_status` 变 `games_playing: []`（机位被摘除） |
| 413.203 s | `op:"message"`（活动领奖通知，与断流无关） |
| 413.255 s | `op:"close"` `{code:0, reason:"normal"}` |
| 413.263 s | 浏览器 `ws-close`，`video.currentTime` 仍靠本地缓冲继续涨 |
| 418.651 s | 同一 token 下出现**另一个 `play_id`** 的会话（被人/别的进程接管） |

**这条路径的特征是：音视频同时停、WS 立刻 close、并且 `games_playing` 已被清空。**
如果你观察到的是「WS 仍 open、心跳仍被回显、只有 RTP 停」，那就不是它，
回到第 2 节的三处差异。

## 5. 给「自己实现媒体栈」的清单

对接 `gw-*.cg.163.com:6443` 时，按重要性排列：

1. **只做一次 STUN 是不够的。** 会话期必须有 ICE consent（2.5 s 周期），
   这是网关判断「对端还在」的唯一周期信号。
2. **answer 不要回 `recvonly`。** 用 `sendrecv`。
3. **`a=extmap` / `a=rtcp-fb` 要回显**，`transport-cc` 最好真的发 TWCC。
4. **RTCP RR / NACK / PLI 是协议义务，但不是保活手段。** 浏览器一次都不发也能收流。
5. **WS 不需要定期心跳。** 头 29 秒之后完全静默是正常现象。
6. **DataChannel 可以不实现。** 浏览器路径根本没有 SCTP m 段；`9 …` 指令可以直接忽略。
7. **`op:"close"` 要当成终止信号**，和 `op:"error"` 分开处理。
8. **`op:"error"` 的 403 / 1213 是「机位没了」**，正确反应是重新申请机位，不是重连。

## 6. 复现方法

本文所有数字都可以用仓库里 `sdk/cgapi.py` + 浏览器复现：

```python
import sys; sys.path.insert(0, 'sdk')
from cgapi import make_api

api = make_api()
api.stop_game('mrfzzmd')                 # 先释放旧机位，否则 400/1811
api.network_test(region='ghnfs', latency=120, bandwidth=60)
tk = api.post_ticket('mrfzzmd', regions=['ghnfs'])
print(tk['gateway_url'], tk['lock_detail'])   # wss://gw-*-hnfs-NN.cg.163.com:6443/ws
```

机位 ttl 只有 **24 秒**，必须「申请即连」。拿到 `gateway_url` 后浏览器打开
`https://cg.163.com/run.html?code=<game_code>`（需先把 `NCG-token` / `NCG-gwurl`
等写进 localStorage，注意 `{"data": <值>}` 信封），再用
`chrome://webrtc-internals` 或 `RTCPeerConnection.getStats()` 观察
`consentRequestsSent` 是否单调递增。
