# 断流与保活：一个非浏览器 WebRTC 客户端会踩的坑

> 抓取与观测日期：2026-11-13 ~ 2026-11-14（北京时间）。所有数据来自真实账号 + 真实机位。
> 本文讨论的是「自己实现 ICE + DTLS-SRTP + RTP 的客户端」（不是浏览器、不是官方 App）
> 对接 `gw-*.cg.163.com:6443` 时，为什么会在若干分钟后**静默丢画面**，以及怎么修。
>
> **本文结论已被自己推翻过一轮。** 第一版把「ICE consent / extmap-rtcp-fb / sendrecv」
> 列为三条修复，理由是「这是网页端与自建客户端的可观测差异」。2026-11-14 用改写
> 网页端行为的方式逐条实测，**三条全部不成立**。第 1、3 节保留原推导作为教训，
> 第 7 节是实测记录，第 8 节是现在的结论。

## 0. 结论先行（2026-11-14 更新）

**截至本文最后一次实测，根因仍未定位。** 但排查空间已经收得很窄：

| 结论 | 依据 |
|---|---|
| 症状是**网关单方面停推 RTP**，不是会话被回收 | 冻结期间 WS 仍 open、`input` 心跳仍被回显、我们发的 ICE consent **仍被正常回应**（`resp` 与 `sent` 同步递增），只有 RTP 停 |
| 停推**不是**任何一条「网页端有、自建客户端没有」的协议差异 | 13 个假设逐一实测否定（含 DTLS cipher 指纹、模拟玩家操作两次真机 A/B），见第 7 节 |
| 官方网页端在同账号同机位能**连续收流 481 s 以上** | 同一套 ticket 接口、同一个 gateway 域名、同一种 `mrfzzmd` 会话 |
| 目前唯一能**定量解释** 250 s 的假设是官方 SDK 的 `RtcKeepPlaying` | `kickoutDuration` 官方取 300000 ms，起播冷启动 + 出画 ≈ 40~50 s，300 − 45 ≈ 255 s；我们从未发过这条帧。卡在 `gameToken` 拿不到，见 §8.2 |
| 有效兜底是**停滞检测 + 原地重连**，不是定期换会话 | `STALLGUARD`（`STALL_RX_MS=8000` 判定 + `L2` 复用同一 ticket 重连）实测 4~9 s 恢复、不丢进度；而「定期换会话」会重新拉起对局容器、游戏从头开始 |

**如果你只是为了「能用」，不要去复刻官方客户端的逐字节行为**——直接按第 5 节的兜底方案做：
`rx` 连续 8 s 不涨就复用同一张 ticket 重连网关。**不要**用「每 250 s 主动换一次会话」，
实测那等于每 4 分钟重开一局（见 §8.3）。

**如果你要继续定位**，第 8.2 节列了剩下的候选方向，按性价比排序。

## 1. 先排除：这几件事**绝对不是**原因

排查「静默停推」最容易走错的四个方向，这里逐条用实测排除。

### 1.1 不是「没响应 DataChannel 握手」

网关会在建连后约 18 s 起，每秒推一次：

```json
{"op":"input","data":{"cmd":"9 25994,1,<4位hex>,<base64>"}}
```

base64 解开恒为 `{"m":"dataChannelReady","pkg":"com.hypergryph.endfield","t":1700000011}`
（同一个 `t` 值**重复推 12 次**后停止；某个会话里推了 32 次）。

**网页端也从不响应它**，并且它照样连着收了 10 分钟。原因在 SDP 里：服务端 offer
**只有 2 个 m 段（audio + video），没有 `m=application` / SCTP**，所以浏览器根本
不会创建 DataChannel（实测 `RTCPeerConnection` 的 `datachannel` 事件从未触发，
`window.__dc` 恒 0）。
`9 …` 这条指令是给「官方原生客户端（走 SCTP）」用的，浏览器端可以直接忽略。

### 1.2 不是「WS 不心跳」

`run.*.js` 里全量搜 `cmd:"0 "` 只有两处：DataChannel 保活、以及 `echoInfo.switch`
的一次性 echo。实测网页端**只在建连时发了 1 次** `{"cmd":"0 1700000010"}`，
网关回显一次，然后 WS 上再也没有任何业务帧，而视频继续流了 8 分钟。

更强的证据：把网页端**所有** `op:"input"` 帧全部丢弃（含那 7 条开播帧和心跳），
仍然连续收流 **481 s**（`video.currentTime` 涨到 477.883，`readyState=4`）。

**结论：WS 通道安静不影响收流。** 不要为了「保活」去加 WS 心跳。

### 1.3 不是「前端无操作超时」（但别和它混淆）

前端自己有一个计时器，参数来自**游戏详情接口**：

```
gameCutTime = { total: 1000*(no_op_duration1 + no_op_duration2),
                warn:  1000*no_op_duration2 }
```

`mrfzzmd` / `wow_cn_high` 实测 `no_op_duration1=480`、`no_op_duration2=120`
→ `total=600 s`、`warn=120 s`。兜底常量在 `.env`：`VUE_APP_CUTTIME_MINUTES=60000`、
`TOTAL=10`、`WRNTIME=2`。

行为：剩 ≤ `warn` 时弹常驻 toast「您还在玩游戏吗？」；到 0 则
`onPostClientError(1002)` + `intervalExitGame()` + ``「由于长时间不操作，已经自动退出」``
+ `closeWindow(10020)`。重置事件：移动端 `touchstart`、PC `keydown`/`click`、
`inputAction` 总线、window `keyup`。

**这是 600 s，而自建客户端实测在 ~250 s 停**，时间尺度差 2.4 倍，不是同一个东西。
（网页端长玩实测确实在 **602 s** 断流，与 `total=600 s` 精确对上——
所以这个计时器是真实存在的，只是它不是自建客户端的那个问题。）

### 1.4 不是「服务端 300 s kickout」（至少在浏览器路径上不成立）

网页端从申请 ticket 起算，在 258 s、300 s、360 s 附近都没有任何异常：
`conn=connected`、`rx` 单调增长、无 `error`、无 `close`。

## 2. SDP 与 getStats 的全量对照（保留作参考）

### 2.1 服务端 offer（约 2,550 B，`a=ice-lite`）

```
a=ice-lite
m=audio 48413 UDP/TLS/RTP/SAVPF 111
a=candidate:1 1 udp 2015364607 27.36.125.184 48413 typ host generation 0
a=ice-ufrag:6N90
a=ice-pwd:jxpQPaD7BUAlPXxXvmJCf4
a=ice-options:trickle trickle
m=video 48413 UDP/TLS/RTP/SAVPF 98 96 107 99 97 108
a=candidate:1 1 udp 2015364607 27.36.125.184 48413 typ host generation 0
```

要点：
- **只有 host candidate**，没有 srflx/relay，端口是网关侧的真实 UDP 端口；
- `a=ice-lite` → 网关不做 connectivity check 的发起方，由客户端提名；
- 音视频复用同一端口（`rtcp-mux`）；
- 视频 6 个 PT（98/96/107/99/97/108），每个都带 `transport-cc` / `goog-remb` / `rrtr`。

### 2.2 浏览器 answer（约 2,705 B）

浏览器回的是 `a=sendrecv` + 原样回显 `a=extmap:*` + `a=rtcp-fb:*` +
`a=ssrc-group:FID` + 两个 `a=ssrc:… cname:` + mDNS candidate。

### 2.3 `getStats()`：20 次 × 5 s 采样（官方网页端）

| 字段 | 起 | 止 | 说明 |
|---|---|---|---|
| `consentRequestsSent` | 5 | 40 | 约 2.5 s 一次，**唯一的周期性双向报文** |
| `responsesReceived` | 6 | 41 | 网关每次都回 |
| `requestsReceived` | 1 | 1 | 网关只发过一次 Binding Request |
| `responsesSent` | 1 | 1 | 我们只回过一次 |
| `bytesSent` | 9,481 | 41,277 | 全是 STUN + DTLS，**几乎不发 RTP** |
| `bytesReceived` | 60,549 | 2,3xx,xxx | 视频下行 |
| `inbound-rtp.video.pliCount` | 0 | **0** | 浏览器一次 PLI 都不发 |
| `inbound-rtp.video.nackCount` | 0 | **0** | 一次 NACK 都不发 |
| `remote-inbound-rtp` | — | **始终缺失** | 网关从不发 RR |

**这张表是后面所有二分实验的出发点**：如果「不发 PLI/NACK/RR」是问题，
那官方网页端自己就该出问题。

## 3. 一个常见的错误推导（保留作教训）

第一版结论是这么来的：

> 网页端 consent 在涨、answer 是 sendrecv + 带 extmap/rtcp-fb，
> 自建客户端三样都没有 → 那一定是这三样的锅。

这个推导错在**把「可观测差异」等同于「致因」**。三处差异确实存在，
但它们只是「网页端恰好这么做」，不是网关判活的依据。要证伪它们，
唯一有效的办法是**让网页端也这么做**，然后看它是否照样断——第 7 节的
`MUNGE=flags` / `MUNGE=full` 就是这个实验。

**教训：想验证「X 是原因」，去掉 X 看是否复现，比「加上 X 看是否消失」更可靠。**
因为「加上 X 之后不断了」可能只是 X 顺手带出了别的效果（比如重连换了新机位）。

## 4. 三条「会话结束」路径，别漏监听

排查停推时如果只监听 `op:"error"`，会漏掉「礼貌下线」这条，
把正常结束误判成网络故障，从而触发不必要的重连逻辑。

| 路径 | 报文 | 前端行为 |
|---|---|---|
| 服务端回收机位 | `op:"error"`，`errcode` ∈ {**403**, **1213**} | 弹「由于您太久没回来游戏已关闭…」，并**自己重 POST tickets 拿新机位** |
| **服务端正常结束** | **`op:"close"`，`{code:0, reason:"normal"}`** | `onGameStop` + `onClose`，**不弹窗、不重连** |
| WS 断开 | `onclose`（无报文） | 显示「正在尝试重新连接，请稍候」，重连 3 次后报 1004 |

`op:"close"` 的真实抓包（2026-11-13，同一次会话）：

| 相对时刻 | 事件 |
|---|---|
| 406.9 s / 412.1 s | `games_playing_status` 里仍是当前会话 |
| 413.199 s | `games_playing_status` 变 `games_playing: []`（机位被摘除） |
| 413.203 s | `op:"message"`（活动领奖通知，与断流无关） |
| 413.255 s | `op:"close"` `{code:0, reason:"normal"}` |
| 413.263 s | 浏览器 `ws-close`，`video.currentTime` 仍靠本地缓冲继续涨 |
| 418.651 s | 同一 token 下出现**另一个 `play_id`** 的会话（被人/别的进程接管） |

**这条路径的特征是：音视频同时停、WS 立刻 close、并且 `games_playing` 已被清空。**

`errcode` 速查：

| errcode | 含义 | 正确反应 |
|---|---|---|
| **403** | 机位没了 / 被回收 | 重新 `POST tickets`，不要原地重连 |
| **1213** | ticket 失效（ttl 24 s）或机位已被抢 | 重新申请机位 |
| **1811** | 上一局还没退干净 | `DELETE api/v2/users/@me/games-playing/<code>` 等 4~6 s 再申请 |
| **1288** | 没有可用 region | 先测速再申请（`regions` 不能为空数组） |
| **0 + `reason:"normal"`** | 正常结束会话 | 走 `onGameStop`，不当故障处理 |

## 5. 保活清单（按「实测有效」排序）

对接 `gw-*.cg.163.com:6443` 时：

1. **停推检测 + 原地重连是最实用的兜底**（`rx` 连续 8 s 不涨 → 复用同一 ticket 重连，
   实测 4~9 s 恢复、不丢进度）。**不要**用「定期主动换会话」：真机实测每次换机位都会
   重新拉起对局容器，游戏从头开始、进度全丢、黑屏 7~9 s（详见 §8.3 的更正）。
2. **WS 不需要定期心跳。** 头 20 秒之后完全静默是正常现象，网页端就这样。
3. **DataChannel 可以不实现。** 浏览器路径根本没有 SCTP m 段；`9 …` 指令直接忽略。
4. **`op:"close"` 要当成终止信号**，和 `op:"error"` 分开处理。
5. **`op:"error"` 的 403 / 1213 是「机位没了」**，正确反应是重新申请机位，不是重连。
6. **`regions` 必须给具体 region code**，空数组会 `404 errcode=1288`。
7. **ticket ttl 只有 24 s**，申请后要立刻 auth，否则 `1213 ticket required`。
8. **RTCP RR / NACK / PLI 是协议义务**（弱网补帧确实需要），但**不是保活手段**：
   网页端一次都不发也能收流 8 分钟；自建客户端全关掉也照样在 250 s 停。
9. **ICE consent 要发**（RFC 8445 §11 的正当行为，且实测网关会正常回应），
   但**发不发不影响停推**。

## 6. 复现方法

```python
import sys; sys.path.insert(0, 'sdk')
from cgapi import make_api

a = make_api()                      # 自动从本机 Chrome 读 token
detail = a.get('api/v1/games/mrfzzmd')
regions = [s['region'] for s in a.media_servers('mrfzzmd')][:1]
tk = a.post_ticket('mrfzzmd', regions=regions, codecs=['h264'],
                   width=1280, height=720)
print(tk['gateway_url'], tk['lock_detail'])   # ticket ttl 仅 24 s
```

拿到 `gateway_url` 后：
1. WS 连上去，**首包 auth 必须明文**（`{"op":"auth","data":{user_id,token,game_code,…}}`）；
2. 之后全部走 `offsetEn(OFFSET, json)`，`OFFSET = get_offset2(cookieGet('NCG-eid')) % 256`；
3. 收到 `op:"offer"` 的 SDP → 建 ICE（ice-lite，主机提名）→ DTLS → SRTP-SAVPF；
4. 观察 `inbound-rtp.bytesReceived` 是否在某个时刻停止增长。

## 7. 2026-11-14 逐项实测：13 个假设，全部被排除

**方法**：第 1–11 条都在**官方网页端**上做（Playwright + iPhone 14 UA + 真实账号 + 真实机位），
用 `addInitScript` 改写网页端发出的报文/SDP，把它改成「自建客户端的样子」，
看官方网页端是否也复现「约 250 s 静默停推」。如果复现 → 假设成立；如果照常连播 → 排除。
第 12 条（DTLS cipher 指纹）与第 13 条（模拟玩家操作）相反：直接在**自建客户端 native 侧**
加开关，真机对照。

这种做法的好处是不需要改一行 native 代码，也不受词典笔硬件影响；
代价是每轮都要重新申请机位（ttl 24 s），而且**必须确认没有第二个客户端在用同一账号抢机位**
（否则每轮都会被顶掉，得到一堆假结论——踩过三次）。

| # | 假设 | 实验 | 结果 | 结论 |
|---|---|---|---|---|
| 1 | 没建 DataChannel | 网页端本来就不建（offer 无 SCTP 段） | 连播 10 min | ❌ 排除 |
| 2 | WS 不心跳 | 网页端本来只发 1 次 | 连播 10 min | ❌ 排除 |
| 3 | 前端 600 s 无操作超时 | 时间尺度对比 | 网页端 602 s 断（对上了），自建客户端 250 s | ❌ 排除 |
| 4 | 服务端 300 s kickout | 258/300/360 s 观察 | 无异常 | ❌ 排除 |
| 5 | 缺 ICE consent | 给 native 补 2.5 s 周期 consent | `resp` 从 #1 涨到 #109，网关全回；**仍在 4m19s 冻结** | ❌ 排除 |
| 6 | answer 不回 `a=extmap`/`a=rtcp-fb` | `MUNGE=flags`：从 answer 里删掉 5 条 extmap + 19 条 rtcp-fb | 连播 **481 s**，`ct=477.883` | ❌ 排除 |
| 7 | answer 是 `a=recvonly` | `MUNGE=full`：再把 `sendrecv` 全改 `recvonly` | 跑到 **354 s** 仍正常（`ct=308.858`） | ❌ 排除 |
| 8 | 上行 RTCP（RR/NACK/PLI）扰乱了网关 | 给 native 加 `noRtcp` 开关，PLI/RR/NACK 全关（consent 保留） | `PLI sent`=0、`RR sent`=0，**仍在 247 s 冻结** | ❌ 排除 |
| 9 | 游玩期不轮询 HTTP，被判挂机 | 记录网页端所有 `/api/` 请求 | 31 个请求全在开头 16 s，之后**零请求**；`users/@me/status` 从未出现 | ❌ 排除 |
| 10 | auth 之后不发任何 input 帧 | 丢弃全部 `op:"input"`（7 条开播帧 + 心跳） | 连播 **481 s**，`ws-close` 为 0 | ❌ 排除 |
| 11 | auth 包内容不同（缺 `fps`/`apk_decoder`，platform 4→1，codecs 15→1，quality high→low，w 1476→1280） | `MUNGE=all`：把网页端 auth 改写成完全等于 native 的形态 | 连播 **284 s**，`ct=284.84`、`rx=50,992,259`，258 s 节点 `ct=254.787` 完全正常 | ❌ 排除 |
| 12 | DTLS ClientHello 指纹（OpenSSL 默认序 28 套件含静态 RSA，vs Chrome 序） | native 加 `chromeFp` 开关：cipher_list 换成 Chrome 序 14 套件（扩展区保持不变），A/B 真机对照 | ClientHello 从 203B→177B（hex 见下），握手照常成功，**停推时刻 237 s 与未改时 230~253 s 完全同量级** | ❌ 排除 |
| 13 | 服务端踢出计时器认「玩家操作」，不发 `keepPlaying` 就按空闲踢 | native 加 `DEV_AUTOTAP` 开关：live 态每 30 s 注入一对真实触摸帧（`cmd 1` 按下 → 120 ms → `cmd 2` 抬起，坐标 (1,1)/(vw,vh)），一局共 16+ 次 | 06:33:55 起流，**06:38:09 会话存活 254 s 时照样停推**（`rx=18865` 冻结），停推时刻与 tap 节奏完全无关 | ❌ 排除 |

第 12 条的实验细节（2026-11-14 06:07 真机）：

- 设备日志确认 `chrome_fp cipher list applied (14 suites, Chrome order)` 生效，
  新 ClientHello：`010000a5…cca9cca8c02bc02fc02cc030c009c013c00ac014009c009d002f003500ff`（15 套件 = 14 Chrome 序 + `00ff` SCUID 重协商点，静态 RSA 全部消失），
  **扩展区 97 字节与默认版逐字节相同**。
- 时间线：06:09:13 出画 → 06:13:10 `stall detected: rx=26133 已 8s 未增长` → 06:13:18 L2 自愈恢复（停滞 5 s）。
  出画到冻结 ≈ **237 s** —— 与不改指纹时的 230/247/248/253 s 完全一致。
- 结论：网关**不是**按「cipher 套件集合/顺序」做风控。JA3 类假说里还剩 extension 集合
  （缺 ALPN 等）与 random 没动，但 ALPN 服务端没选，加了也未必等价，优先级降低。

完整 hex 与解析见 PenCG 侧 `docs/DTLS-CLIENTHELLO-FINGERPRINT.md`（默认 203B 与 chrome_fp 177B 两版）。

第 13 条的实验细节（2026-11-14 06:33–06:38 真机，原神 `yssy`，网关 `gw-lt-hbtj-03`）：

- 为什么做这一条：官方 SDK 的 `keepPlaying()`（`CmdId=20015`）**只在玩家操作时发**，
  不是周期心跳。如果服务端的踢出计时器认的是「有操作就不踢」，那我们只要周期性注入
  真实输入帧就能续命 —— 这是客户端侧唯一还没试过的「行为层」差异。
- 实现：不依赖不稳定的 `send_event touch slip`，直接在 play 页 tick 里调 native 的输入接口，
  构造真实的 `cmd 1`（down）/`cmd 2`（up）帧，与用户真手指产生的报文同格式。
- 时间线：06:33:46 `boot code=yssy` → 06:33:55 wsOpen id=1 → 06:34:08 出画（audio=1）→
  autotap 每 30 s 一次，共 16+ 次 → **06:38:09 `stall detected: rx=18865 已 8s 未增长`**
  → 06:38:12 L1 → 06:38:16 L2 复用网关重连 → recovered `rx=119`（停滞 5 s）。
- 结论：会话存活 **254 s**，与从不注入触摸的 230/247/248/250/253/259/260/263 s 完全同分布。
  **服务端踢出计时器不认「玩家操作」这个信号**（至少不认我们这种注入方式）。
  至此客户端侧可做的实验全部做完。

第 11 条是最后一条「协议层可见差异」。改写后的 auth 实测报文（token 打码）：

```json
{"id":"<Date.now()>","op":"auth","data":{
  "user_id":"…","token":"<token>","game_code":"mrfzzmd",
  "w":1280,"h":720,"quality":"low","codecs":["h264"],"platform":1}}
```

——与自建客户端发出的完全一致，网关接受（回了 `op:offer`），并且不因此停推。

### 7.1 一个重要的附带发现

冻结期间我们发出的 ICE consent **仍然被网关正常回应**：

```
[cgmedia] #1 ICE consent sent (#97, every 2500ms) resp=98  rxStun=108
（此时 RTP 已停了 12 s）
```

说明**网关没有把这个会话丢弃**，UDP 五元组是活的、我们的报文它照收照回。
它是**单独停掉了 RTP 的推送**。

这条事实很重要：它排除了「会话被回收 / NAT 超时 / 端口失效」这一大类解释，
把问题锁定在网关**媒体层**的某个判定上。

### 7.2 第 12 轮：从设备侧取到三个新事实（2026-11-14 03:40）

这一轮没有再改网页端，而是直接在自建客户端加日志、再看真机输出。三条都影响后面的排序。

**(1) DTLS 握手参数（此前从未取到过，三次会话完全一致）**

```

```

对应代码 `cm_dtls.c`：`:350 SSL_CTX_new(DTLS_client_method())`、
`:352 SSL_CTX_set_tlsext_use_srtp(ctx, "SRTP_AES128_CM_SHA1_80")`、
`:355 SSL_CTX_set_verify(ctx, SSL_VERIFY_NONE, NULL)`、`:356 SSL_CTX_set_read_ahead(ctx, 1)`、
`:357 SSL_CTX_set_options(ctx, SSL_OP_NO_TICKET)`、`:392 SSL_set_mtu(ssl, DTLS_MTU)`。
**没有设 `min/max_proto`、没有设 `cipher_list`、没有设 `extended_master_secret`** —— 全走 OpenSSL 默认。

DTLS 报文序列（`grep 'DTLS hdr'`）也是三次一致：
`ct=22 ver=fefd epoch=0000 len=110` → `len=457` → `len=213` → `len=66` → `len=12`
→ `ct=20 epoch=0000 len=1`（ChangeCipherSpec）→ `ct=22 epoch=0001 len=40`（加密的 Finished）→ `DTLS OK`。
`ver=fefd` 即 DTLS 1.2，Finished 在 epoch=1，握手本身完全规范。

**(2) 第一个媒体包的序列号不是 0**

`cm_srtp_unprotect` 的前 8 条 dump 里第一条是
`roc=0 seq=31394 ssrc=ca8d65a6 pt=98 x=1 extw=0 hl=32 len=65 pl=23` ——
**第一个包就已经在 31394**，机位下发的是连续递增的序列号。

**(3) 实测包率 ≈ 80 pkt/s**

`rx`（通过 SSRC 校验的 RTP 包数）每 20 s 稳定 +1600；`play.vue` 的 probe 注释同样写
「正常播放时 rx 每 20s 稳定 +1600（≈80 包/秒，fps 29~30）」。
注意不能用 `rxPkts`（socket 上的 datagram 总数，含 STUN/DTLS）——停推之后 ICE 保活的 STUN
照样在涨，拿它判停滞会永远判不出来（真机验证过）。

**(4) 顺带发现的两个工具层缺口**

- `cm_srtp.c:369` 的 dump 条件是
  `if (s->stats.srtp_auth_fail + (uint64_t)s->stats.rtp_rx < CM_SRTP_DUMP_MAX)`，
  `CM_SRTP_DUMP_MAX = 8`（`cm_srtp.c:104`）—— **只打开头 8 个包，之后永久静默**。
  想观察冻结前后的 `seq`/`roc` 必须先把这个条件改成周期性。
- native 每 2 s（`cm_media.c:16 STAT_INTERVAL_MS 2000`）发的 stat JSON **不进设备日志**：
  `cm_emit()` 走 JSAPI 回调给 `play.vue`，由它拼成 `[play] probe ...` 才落盘，
  且只带 `ev.rx/lost/bitrateKbps/fps/kf/pli/gateDrop/auDrop/kfReq/w/h` 这些字段。
  **要在设备日志里看新计数，只能在 native 侧直接 `CM_LOGI`**（`CM_LOGD` 默认 `log_level=3` 不打印）。

## 8. 现在的判断

### 8.1 已确定的事实

1. 官方网页端（Chrome）在同账号、同 ticket 接口、同 gateway 域名、同 `mrfzzmd` 会话下，
   **能连续收流 481 s 以上**，且在 8 分钟窗口内不出现任何停推；
2. 自建客户端每次都停在 **~250 s**（11 局实测：247 / 248 / 250 / 252 / 253 / 254 / 258 / 259 /
   260 / 261 / 263 s），`rx` 冻结、`fps` 归零，但 WS 健康、consent 被正常回应；
3. 第 7 节 13 个假设全部排除，其中包含所有「网页端发/收、自建客户端不发/不收」的报文级差异、
   DTLS cipher 指纹（第 12 条，真机 A/B），以及模拟玩家操作（第 13 条，真机 A/B）。

**关于「250 s」的口径（重要，容易被误读）**：

- 计时的**起点是每次 `wsOpen`**，不是「申请 ticket」也不是「进程启动」。
  这一点由 L2 重连后重新计时证实：06:38:16 L2 重连成功 → 下一轮停推在 ~4 分钟后再次出现，
  而不是「立刻又停」。
- 停推时刻**与起播延迟无关**：同一台设备、同一网关，出画早 8 s 或晚 20 s，
  停推都落在 wsOpen + 250 s 附近，说明是**服务端从握手完成的时刻起算的定时器**，
  而不是「出流 N 帧后停」这种按媒体计数的逻辑。
- **250 s 与「官方 kickout = 300000 ms」相差约 45~50 s**，正好等于「wsOpen → 出画」的冷启动耗时
  （实测 13~45 s 不等，平均 ~40 s）。这与「服务端在 kickout 到期时停推，而我们的出画比官方晚」
  的模型一致 —— 也就是说**用户真正能玩的时间 = 300 s − 起播耗时**，
  这也解释了为什么偶尔看到 230 s、偶尔 263 s。
- **一个尚未解释的例外**：2026-11-14 05:56:50 有一局在 **108 s** 就被 `op:close {code:0,reason:"normal"}`
  关掉了（见 `docs/API文档.md` §8.6.3 的补充）。它带 close 帧、且远早于 250 s，
  属于「主动关闭」而非「定时停推」，不能用来推翻 250 s 模型。

### 8.2 剩下的候选方向（按性价比排序，2026-11-14 09:40 更新）

第 13 条实验后，客户端侧能想到的行为差异也清空了。排序再次变化，
**第一优先变成了一个「协议上有明确名字」的方向**：

1. **官方 SDK 的 `RtcKeepPlaying` 帧（`CmdId=20015`）—— 唯一「机制明确、且尚未排除」**。
   官方 RTC SDK 除了我们复刻的那条 JSON 网关（`gw-*.cg.163.com:6443/ws`），还有第二条通道：
   `channel 2`，端点是 `<gameServerWssUrl>` 强制加 `/rtc-sdk`，帧格式是
   `'Eg' + cmdId + len + 0x89 0xAB + protobuf` 的**二进制**（与我们这条 JSON + 每字节 +72 + base64
   完全不同）。这条通道上有两个和「保活」直接相关的命令：

   | CmdId | 消息 | 关键字段 |
   |---|---|---|
   | 20021 | `RtcKeepaliveCfg` | 字段 1 `kickoutDuration`（ms）、字段 2 `tipsDuration`（ms） |
   | 20015 | `RtcKeepPlaying` | 字段 1 `gameToken`（string） |
   | 20014 | `RtcNotPlayingTips` | 服务端下发「太久没回来」提示 |

   官方 `setReady()` 会先发 `setKeepAliveConfig(kg(5), 20000)`，即
   **`kickout=300000 ms`（5 分钟）/ `tips=20000 ms`**；而 `keepPlaying()`
   **只在玩家真正操作时发**，不是周期心跳。我们两条都没实现，服务端只能用默认的短 kickout
   —— 250 s 与「默认 kickout 略小于 300 s」高度吻合（起播冷启动 + 出画延迟 ≈ 40~50 s，
   300 - 45 ≈ 255 s）。这是目前唯一能**定量解释** 250 s 的假设。

   **卡点（为什么还没做）**：`keepPlaying` 的 `gameToken` 唯一来源是
   `POST /dispatcher/api/paasDispatch` 的 `finish_result.sdk_param`
   （`proto.paas.SdkStartGameParams` 字段 4），而该接口需要官方 web 包内嵌的
   `appEnv.appKey` 做签名，目前拿不到。我们自己的 `api/v2/tickets` 响应、
   `op:result`、`games_playing_status`、10 份落盘 SDP 里**全都没有 gameToken**
   （唯一的 token 是用户级 JWT，不是会话级 gameToken）。
   ⇒ **要推进这条线，必须先解决 `paasDispatch` 的签名**，这是当前最高价值的单点。
2. **DTLS extension 级指纹**（上一轮的第一优先降级于此）：cipher 序已实测无效，
   但扩展集合仍有差异 —— 自建客户端没有 ALPN、没有 supported_versions、
   use_srtp 只列 `SHA1_80`（Chrome 是 `AEAD_AES_128_GCM` 在前）。
   ALPN 服务端没选，这条属于「半协议语义」差异，做 A/B 成本高、命中概率中。
3. **`op:result` 的 container 后缀分档**。`encoder` 两边一样，但容器后缀不同：

   | 端 | container 后缀 | host | encoder | 结局 |
   |---|---|---|---|---|
   | 自建客户端 | `t-04` | `ahnfs10000` | `high,None` | 230 s 冻结 |
   | 网页端 | `t-18` | `ahnfs10000` | `high,None` | 481 s 未冻结 |

   `encoder` 两边一样，说明这个字段本身不是判据；`container` 后缀不同，值得每轮都记下来
   —— 凑够样本才能判断是「某些容器类型有问题」还是「纯巧合」。
   **`host` 目前只有一条实测样本（`ahnfs10000`，见 `docs/API文档.md` §7.1.1），两端相同，
   所以「host 不同」这一点没有证据支撑**（README 早期版本误写成 `ahnfs10015`/`ahnfs10007`，已更正）。
4. **账号/时长策略**。如果最终对不上任何协议侧差异，就只能接受「网关按会话时长/账号行为
   对非浏览器 UA 做软限」的解释 —— 无法从客户端侧修，只能靠兜底（见 §8.3）。
   （SRTP ROC 与 UDP 缓冲这两个更早的候选已在前几轮按实测排除：ROC 起始
   `seq=31394`、80 pkt/s，回绕需 ≈427 s 与 230~250 s 冻结对不上，且 SRTP 认证 0 失败；
   UDP 缓冲与 `rxStun` 同步增长矛盾。）

### 8.3 工程上的建议

> **⚠ 本节早期版本是错的，已更正。** 原文写「每 ~230 s 主动换一次会话，
> 用户侧表现是画面卡 1~2 秒」，实测证明这个说法严重低估了代价。

**不要用「定期主动换会话」做保活。** 真机实测（把 `ACTIVE_RENEW_MS` 降到 60 s，
连做三次）：每次换机位都会**重新拉起对局容器** —— 游戏从头开始、进度全部丢失，
黑屏 9 / 8 / 7 s，音频恢复 11 / 19 / 18 s。这不是「卡 1~2 秒」，是「每 4 分钟重开一局」。
该策略最终被设为默认关闭（`ACTIVE_RENEW_MS = 0`）。

**正确做法是「停推检测 + 原地重连」**（PenCG 里的 `STALLGUARD`）：

1. 每秒看 `rx` 是否增长；连续 **8 s** 不涨即判定停推（正常码率下 8 s 必涨）；
2. L1：补发关键帧请求（PLI + 3 连发，间隔 400 ms），等 5 s；
3. L2：复用**同一张 ticket** 重连网关（不重新 `POST tickets`、不换机位），
   实测 4~9 s 恢复、进度不丢；
4. L3：L2 仍失败才重新申请机位（会丢进度，但对 `op:close` 类硬踢只能如此）。

实测数据：7 局里有 6 局 L2 在 4~9 s 内救回；最慢一次 26 s，那一局是网关在 108 s
主动发了 `op:close {"code":0,"reason":"normal"}`（属于硬踢，必须 L3 换机位）。
